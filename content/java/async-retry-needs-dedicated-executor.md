## 看起来省事，实际上最容易互相拖垮

很多 Java 服务在第一次接入重试时，写法都差不多：主流程里发起一次远程调用，失败了就提交一个异步任务延后再试。
因为项目里已经有业务线程池，最顺手的做法往往是把重试任务也丢进去，觉得这样可以少配一套资源、少记一份参数。

短时间看，这种做法确实很方便。但只要流量一上来，或者下游服务开始抖动，问题就会很快暴露出来。业务线程池本来负责
处理正常请求，现在又额外承担重试任务。一次调用失败，不只是多一次请求，而是多出一串延后的补偿动作。失败越多，
排队越长；排队越长，正常请求越慢；正常请求越慢，又会制造更多超时和失败。最终形成一个自我放大的回路。

所以“异步重试别和业务线程池混在一起”并不是一条形式化规范，而是一个很现实的容量边界。

## 为什么共用线程池会放大故障

线程池的本质，是用有限线程去承接一类相似时延特征的任务。正常业务请求通常希望尽快完成，排队时间越短越好；
而重试任务天然带着失败历史，执行时间更不稳定，还可能伴随退避等待、幂等检查、状态补写和额外日志。

当这两类任务混在一起时，会同时出现几个问题：

- 正常流量和异常流量争抢同一批工作线程。
- 重试任务往往在故障期集中堆积，容易把队列瞬间填满。
- 业务方看到线程池繁忙，只会感知“系统整体变慢”，但很难第一时间分辨到底是正常请求多，还是重试拖住了资源。
- 一旦拒绝策略触发，最容易被拒绝的未必是低优先级重试，反而可能是新的在线请求。

这也是为什么很多线上事故在复盘时会发现，真正拖垮系统的不是第一次失败，而是失败后的补偿流量和正常流量没有隔离。

## 先把重试当成独立工作负载

异步重试更合理的做法，是把它当成一类独立工作负载来设计，而不是“主流程失败后的顺手补丁”。

最基本的一步，就是给重试任务单独的执行器。即便初期线程数不大，也要让它和主业务池分开，这样至少能保证两件事：

- 下游故障时，重试任务最多把自己的池子打满，不会直接挤占主请求线程。
- 监控上可以清楚区分哪部分容量消耗来自在线流量，哪部分来自异常恢复。

例如：

```java
@Bean
public ScheduledExecutorService retryScheduler() {
    return new ScheduledThreadPoolExecutor(
        4,
        new ThreadFactoryBuilder().setNameFormat("order-retry-%d").build(),
        new ThreadPoolExecutor.AbortPolicy()
    );
}
```

如果重试不是按固定延时调度，而是交给消息队列或延迟队列处理，原则也一样：通道可以不同，但执行容量和业务主路径要隔离。

## 只隔离线程池还不够，还要限制重试本身的形状

很多人做了线程池隔离以后，就觉得问题已经解决了一半。实际上，如果重试策略本身没有约束，单独的线程池只是把故障
从“拖垮全站”变成“拖垮重试系统”。

比较稳妥的重试设计，通常还需要同时满足下面几点：

### 限制最大重试次数

无限重试本质上是在把一次失败变成持续负债。大多数业务场景里，超过 3 次到 5 次后，成功率提升已经很有限，
却会明显加重下游压力。

### 做退避，而不是立刻重放

如果下游已经处于高延迟或半故障状态，立刻再试通常只会把拥塞复制一遍。指数退避配合随机抖动，能减少重试同时涌入：

```java
long delayMillis = Math.min(baseDelayMillis * (1L << attempt), maxDelayMillis);
long jitter = ThreadLocalRandom.current().nextLong(100, 300);
retryScheduler.schedule(task, delayMillis + jitter, TimeUnit.MILLISECONDS);
```

### 明确哪些异常值得重试

超时、临时网络错误、下游限流等，通常属于可重试异常；参数错误、业务校验失败、幂等冲突等，则应该直接结束。
如果不区分异常类型，系统就会把“本来不可能成功”的请求一遍遍重放。

### 保证幂等

重试只是把同一意图重新执行，不应该把结果重复落库、重复扣款或重复发通知。没有幂等前提的重试，恢复能力越强，
副作用往往越大。

## 观测重点不是“有没有重试”，而是“重试有没有反过来伤害主流程”

线上治理里，重试最容易缺的是可观察性。很多服务只能看到错误率升高，却看不到重试队列长度、重试成功率和平均等待时间。
这样一来，团队会误以为“线程池参数不够大”，然后继续扩容，把问题藏得更深。

更有价值的指标至少包括：

- 当前重试队列长度。
- 每分钟新增重试任务数。
- 不同尝试次数的成功率分布。
- 因达到最大次数而放弃的任务量。
- 重试线程池活跃线程数与拒绝次数。
- 主业务线程池和重试线程池的耗时、拒绝、排队时长对比。

只要这些指标摆在一起，很多问题会非常直观。比如主线程池耗时突然上升，但重试池也同时打满，就说明故障已经从下游扩散到恢复机制本身；
如果重试量暴增但成功率持续很低，就应该先降重试频率，而不是继续堆机器。

## 更稳的目标不是“失败后一定追回来”，而是“失败时别把系统一起带走”

异步重试当然有价值。它能减少瞬时失败带来的业务损失，也能帮系统穿过一些短暂抖动。但前提是，重试本身必须被当作一种
有成本、有风险的能力来建设。

共用业务线程池的问题，不在于代码写法不优雅，而在于它默认“恢复动作和主流程是同一种负载”。这在顺风时期不明显，
在逆风时期却最容易出事。

把重试线程池独立出来、限制重试次数、做退避和异常分类、补齐监控指标，这几步并不复杂，却能显著降低失败扩散的速度。
真正稳的系统，不是失败时拼命多试几次，而是知道哪些重试值得做，做的时候又不伤到主路径。

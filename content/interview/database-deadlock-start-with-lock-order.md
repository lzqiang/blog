## 先别急着背定义，先说死锁长什么样

面试里一提到数据库死锁，很多人会先给一句标准答案：两个事务互相等待对方释放资源，最后谁都走不下去。
这句话没错，但只停在这里，通常不够。

更好的讲法，是把场景说具体。比如事务 A 先更新订单表，再更新库存表；事务 B 先更新库存表，再更新订单表。
如果两个事务几乎同时进入，各自先拿到第一把锁，再去等第二把锁，就会形成一个环。

死锁的关键不是“慢”，也不是“锁多”，而是等待关系闭环了。

## 面试官真正想听的，是死锁为什么会发生

数据库里的死锁，常见来源通常有这几类：

1. 多个事务访问同一批数据，但顺序不一致。
2. 范围查询和更新混用，导致锁范围比预期更大。
3. 没有命中索引，行锁退化成更大范围的扫描锁。
4. 一个事务里做了太多事情，持锁时间过长。

其中最常见、也最值得优先讲清楚的，就是加锁顺序不一致。

因为它最容易复现，也最容易解释业务场景。比如转账、扣库存、状态推进这类操作，本质上都是“改多行或多表”。
只要不同入口对资源的访问顺序不统一，系统流量一高，就容易撞出死锁。

## 诊断时别先说重启，先说你怎么看等待链

如果面试官继续追问怎么排查，别直接说“重试”或者“重启数据库”。这类回答会显得只会补救，不会定位。

更稳的回答顺序通常是：

1. 先从数据库告警或应用报错里确认是否真的是死锁，而不是普通锁等待超时。
2. 查看死锁日志，找到涉及的两个事务、SQL 语句和锁对象。
3. 对照执行计划，看 SQL 是否走了预期索引。
4. 结合业务代码，确认事务里的操作顺序是否一致。

像 MySQL InnoDB，一般可以通过死锁日志看到“谁持有锁、谁在等待哪把锁”。这一步的价值很大，因为它能帮助你从“系统很卡”回到具体 SQL 和具体数据行。

如果回答里能明确区分“死锁”和“锁等待超时”，面试官通常会觉得你不是只背过八股，而是真的碰过线上问题。

## 真正有效的治理，通常不是把超时时间调大

很多人遇到数据库并发问题，第一反应是把超时时间调大，或者给事务多做几次重试。
这些手段有时能缓一口气，但通常不是根治。

更有效的办法，往往是下面几类：

1. 统一业务里的加锁顺序，比如都先改主表，再改明细表。
2. 缩短事务范围，不要把查询、远程调用、复杂计算都包进事务。
3. 给更新条件补齐索引，避免扫描过多无关数据。
4. 对高冲突热点记录做拆分，减少所有请求都抢同一行。

这里面最值得优先强调的，仍然是统一顺序。因为只要顺序一致，很多本来会闭环的等待关系，就只剩下单向排队，不容易形成死锁。

## 最后补一句：死锁不一定代表数据库差

面试里如果能再往前走一步，效果会更好。你可以补充一句：死锁并不一定说明数据库有问题，它往往说明并发访问模型和业务更新路径设计得不够稳定。

数据库只是把矛盾暴露出来了。

真正成熟的处理方式，不是指望数据库“别死锁”，而是让应用层的事务设计、SQL 访问路径、资源顺序足够一致。
这样回答下来，面试官一般会认为你理解的是并发控制本身，而不只是一个报错名词。

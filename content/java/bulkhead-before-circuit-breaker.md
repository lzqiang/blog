## 熔断很重要，但它不是第一层防线

服务一旦调用多个下游，线上迟早会遇到这样的场景：某个依赖开始变慢，错误率不一定立刻飙高，可接口耗时已经明显拉长。很多团队的第一反应是赶紧给
这个下游加熔断，想用快速失败把主流程保住。这个方向没有问题，但如果系统还没做资源隔离，熔断往往来得太晚。

原因很简单。熔断器的判断依据通常是最近一段时间的失败率、慢调用比例或者并发量阈值。也就是说，系统要先积累一批足够“糟糕”的请求，熔断规则才会
动作。在这之前，线程、连接和请求预算已经先被慢调用占住了。你看到的现象通常不是“某个下游报错很多”，而是“整条链路都开始排队”。

所以在 Java 服务治理里，真正该先做的不是争论熔断窗口怎么配，而是先把不同依赖隔开，避免一个坏掉的下游把别的路径一起拖慢。

## 为什么没有隔舱时，熔断救场能力很有限

很多人把熔断理解成“发现下游不行就别再调了”。问题在于，如果所有调用都共用同一个 Tomcat 工作线程池、同一组 HTTP 连接池或同一个异步执行器，
那么下游变慢的影响会先体现在资源占满上。

常见的连锁过程通常是这样的：

- 订单接口发起调用时，本来应该在几十毫秒内拿到库存结果。
- 库存服务开始抖动后，每个请求要卡住两三秒。
- 工作线程迟迟不释放，等待中的请求越来越多。
- 上游超时增多，重试、补偿或前端刷新又把流量再推高一层。
- 熔断规则终于触发时，线程池和连接池其实已经挤满，别的正常依赖也开始受牵连。

这时即便熔断已经打开，系统也未必立刻恢复，因为前面排队积压下来的请求还在消耗时间。换句话说，没有隔舱时，熔断更像“止损”，而不是“隔离故障”。

## 隔舱的本质，是先决定谁不能互相拖累

“隔舱”这个词来自船体设计：某一段进水时，先把损害限制在局部，别让整艘船一起沉。放到后端服务里，意思就是为不同调用路径准备独立的资源边界。

最常见的隔离对象包括：

- 线程池：不要让多个重要性不同的下游共享同一个异步执行器。
- 连接池：对高风险依赖单独分配连接容量，避免把全局连接耗尽。
- 超时预算：给每个下游设置符合业务价值的超时上限，而不是统一一个大值。
- 限流阈值：在入口就限制某类请求的最大并发，而不是等它们把内部资源打满。

很多项目里，线程池隔离是最容易落地的一步。比如商品详情页要同时查商品、库存和推荐，如果推荐服务只是锦上添花，就不应该和商品、库存共用同一组
执行资源。推荐抖动时，最多让推荐位为空，而不是把商品主信息也一起拖死。

## 先隔舱，熔断策略才有真正落点

隔离资源后，熔断配置才会变得有意义。因为这时熔断器面对的是一类明确、边界稳定的调用流量，而不是混杂在一起的全局资源池。

比较稳妥的做法通常是：

1. 先给关键下游划分单独线程池或连接池，限制它最多能占多少容量。
2. 再根据该下游的正常耗时和错误特征设置超时、慢调用阈值和熔断窗口。
3. 最后补上降级逻辑，明确熔断后返回什么默认值、空结果或兜底提示。

例如一个营销推荐接口平时耗时 120 毫秒，业务上允许它短时间不可用，那么它可以使用更小的线程池、更激进的超时和更快打开的熔断规则。相反，支付确认
这种关键路径，即便也要做熔断，也应优先考虑幂等、补偿和人工兜底，而不是简单返回一个默认成功。

## 配置层面最容易犯的几个错

在生产系统里，很多“明明配了熔断却还是雪崩”的情况，本质上都不是熔断器失效，而是前置隔离没有做好。常见误区有三个。

第一，把所有下游都放在一个大线程池里，觉得这样利用率更高。短期看资源不会空着，长期看却意味着任何一个慢依赖都能影响所有路径。

第二，超时时间只看业务方的心理安全感，不看系统总预算。有人担心误伤，就把下游超时统一设成三秒、五秒，结果调用量一大，线程被挂住的时间也同步放大。

第三，只统计错误率，不盯慢调用比例。很多雪崩不是从报错开始，而是从“成功但很慢”开始。等真正积累出失败率时，容量往往已经被吃掉大半。

## 观测上要看局部资源，而不是只看接口成功率

要验证隔舱是否有效，不能只盯接口 200 比例。更有价值的是看每个依赖对应的局部资源指标：

- 独立线程池的活跃线程数、队列长度和拒绝次数。
- 连接池使用率、等待时长和超时次数。
- 单个下游的 P95、P99 耗时与慢调用占比。
- 熔断打开次数、半开恢复成功率和降级命中量。

这些指标放在一起看，才能判断系统到底是“下游真的坏了”，还是“隔离做得不够，坏影响还在扩散”。如果某个推荐服务线程池已经满了，但订单主链路线程池
依然稳定，那说明隔舱在起作用；如果两个池子一起打满，就要继续追查是否还共享了数据库连接、公共缓存或入口限流阈值。

## 真正稳的顺序，是隔离、限时、降级，再熔断

熔断不是不重要，而是它最适合放在已有边界之上，充当加速失败和恢复的控制器。没有隔舱时，熔断器看到的只是已经蔓延开的后果；先把资源边界画出来，
它才能在局部范围内快速动作。

所以如果团队正在治理一个频繁被下游拖慢的 Java 服务，不妨先问四个问题：这个下游有没有独立线程池，是否有明确超时预算，降级结果是否定义清楚，
它最多能拖累多少请求。如果这几个问题还没答清，先别急着把注意力全放在熔断参数上。

先做隔舱，再谈熔断，系统的韧性通常会来得更早一些。

## 停机不是一条 kill 命令

服务发布时，最容易被忽略的时刻往往是旧实例退出的那几十秒。要是进程直接结束，
正在处理的请求、还没提交的消息确认、排在执行器里的异步任务，都可能被半途截断。
用户看到的是一次偶发失败，系统里留下的却可能是一笔状态不完整的数据。

因此，优雅停机不是“等一会儿再退出”这么简单，而是为旧实例安排一段有顺序的退场：
不再接新活，处理完手里的活，再关掉依赖和线程。

## 第一步：让流量先离开

应用收到 `SIGTERM` 后，首先要做的是把自己从可接流量的实例中移开。对 HTTP 服务来说，
这通常意味着就绪检查返回失败，让负载均衡器不再分配新请求；对消息消费者来说，
则是暂停拉取或撤销消费资格。

这里有一个常见误区：以为关闭监听端口就够了。实际上，负载均衡器、服务注册中心和客户端连接池
都有自己的刷新周期。更稳妥的做法是先切换为 not ready，再等待一个短暂的传播时间，
然后才开始关闭 Web Server。这样，正在路上的请求会少得多。

## 第二步：给正在执行的任务设一个期限

停止新流量后，应用仍要保留已经进入系统的工作。同步请求需要等业务逻辑和响应写回完成；
异步任务则需要让线程池进入 `shutdown()` 状态：拒绝新任务，继续执行队列中已有的任务。

但等待不能没有上限。可以根据接口的 P99 耗时、下游超时和任务队列长度，为停机设置一个明确的
grace period。例如大多数请求能在 15 秒内完成，就给 30 秒；如果超过期限仍有任务卡住，
记录任务数量与堆栈，再执行兜底退出。无限期等待会把一次发布变成容量事故。

```java
executor.shutdown();
if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
    executor.shutdownNow();
}
```

这段代码只是最后一环。真正重要的是，任务本身要能响应中断，并且外部调用必须有合理的连接与读取超时；
否则 `shutdownNow()` 只是在发出中断信号，不能保证立刻停止。

## 第三步：按依赖方向关闭资源

资源关闭的顺序应与启动顺序相反。先停止入口，再停止业务执行器和消费者，最后才关闭数据库连接池、
HTTP 客户端、日志组件等底层资源。要是先关了数据库连接，正在执行的事务只能以更难排查的方式失败。

同样，消息消费场景里不要在业务任务尚未确认之前就断开客户端。否则 broker 会把消息重新投递，
而旧实例和新实例可能在短时间内同时处理同一业务。幂等是必要的保护，但不该被当作粗暴停机的借口。

## 把停机过程变成可观察的过程

一次好的优雅停机，应当能从日志和指标里看清楚：何时停止就绪、当时有多少活跃请求、
线程池还剩多少任务、最终是自然结束还是超时强退。发布后若出现少量失败，这些信息能迅速判断
问题在流量摘除、任务耗时，还是资源关闭顺序。

服务的启动决定它怎样开始工作，停机则决定它怎样把工作交出去。先停止新任务、再等待存量任务、
最后关闭资源，这个顺序看起来朴素，却能避免很多只在发布窗口出现的偶发故障。

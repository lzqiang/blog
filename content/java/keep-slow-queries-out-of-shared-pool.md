## 共享线程池最怕的，不是忙，而是被同一种慢任务拖住

很多 Java 服务一开始都会把普通请求、定时任务、补偿任务、报表任务放在同一个线程池里跑。这样做简单，
但也埋了一个隐患：只要其中一类任务明显变慢，其他任务就会跟着一起受影响。

最典型的情况是慢查询。某个接口里顺手查了一次表，平时几十毫秒，某天因为索引失效、数据量上涨或者锁竞争，
变成了几秒。只要它还在共享线程池里占着线程，后面的快请求就只能老老实实排队。

## 线程池不是隔离层，它只是排队器

很多人会把线程池想成“并发越多越好”的地方，但线程池真正做的事情其实很朴素：限制并发、承接排队。
如果所有任务都进一个池子，线程池就会把不同性质的工作混在一起处理。

这时候最危险的不是慢任务本身，而是慢任务把快任务的响应时间一起拉长。

1. 快请求会被慢请求占住线程。
2. 队列长度会跟着变长。
3. 超时和重试会把流量进一步放大。
4. 最后看起来像“系统整体不稳定”，其实只是一个共享池被拖慢了。

## 先把任务分层，比盲目扩容更有效

如果任务类型差异很大，我通常会先做隔离，而不是先加线程。

1. 用户请求和后台批处理分开。
2. 读操作和写操作尽量不要共池。
3. 对外 RPC 和本地计算分开。
4. 预期会慢的任务单独限流。

这样做的好处是，慢任务就算退化，也只影响它自己那一层，不会把整个服务一起拖进排队地狱。

比如报表导出、补偿重试、批量同步这类任务，本来就不该和在线请求争抢同一批线程。它们可以慢一点，
但在线请求不能跟着一起慢。

## 真遇到慢查询，先看三件事

如果线程池开始堆积，我会先确认三件事。

1. 任务是不是集中卡在数据库或远程调用上。
2. 慢任务是不是集中在某个固定入口。
3. 超时和重试有没有把问题放大。

只要慢点清楚了，解决办法通常也就清楚了：补索引、改 SQL、缩短超时、降低重试次数，或者直接把这类任务拆到单独线程池。

## 共享池适合轻任务，不适合把所有风险都装进去

共享线程池最大的价值，是方便；最大的代价，也是方便。它让所有任务都能迅速跑起来，
但也让所有任务更容易一起被拖慢。

所以只要任务有明显的慢快差异，我都会优先考虑隔离。线程池不是越大越好，能把慢查询留在自己的池子里，
才更接近真正的稳定。

## Stream 看起来干净，不代表它适合承载副作用

很多 Java 代码在重构时，都会把 `for` 循环改成 Stream。改完以后，代码往往更短，也更像“声明式”表达：
先筛选，再映射，再聚合，阅读体验确实更整齐。问题在于，团队很容易在这种整齐里继续塞东西，
最后把本应显式处理的远程调用也一起放进 `map`、`filter` 或 `peek`。

例如一段用户列表处理逻辑，本来只是遍历用户并组装展示对象，后来为了补充头像、积分、标签等字段，
就开始在 `map` 里调用用户中心、积分服务和标签服务。代码表面上依然只有十几行，
但每个元素背后都可能触发三四次网络请求。等到线上接口变慢，日志里只剩一串优雅的链式调用，
排查的人却很难一眼看出慢点到底埋在哪一步。

Stream 适合描述“数据如何变形”，不适合隐藏“系统正在做多少外部动作”。
一旦副作用被压进流水线里，复杂度不会消失，只会被藏起来。

## 为什么远程调用塞进 Stream 后更难排查

第一层问题是观测性变差。`for` 循环里做远程调用时，通常会顺手把请求参数、批次大小、
耗时统计或降级分支写得比较明确。换成 Stream 后，很多人倾向于把逻辑压缩成一个 lambda，
只留下“看起来很函数式”的主干，结果副作用的边界被藏进匿名函数里。

第二层问题是异常处理变形。Stream 的 lambda 里不能自然抛受检异常，开发者常常会包装成运行时异常，
或者在内部捕获后返回默认值。短期看代码通了，长期看却把错误语义弄混了：
到底是业务上确实没有数据，还是远程调用失败被吞掉了，调用方根本分不清。

第三层问题是性能模型不透明。对一段循环代码，你很容易数出每次迭代做了几件事；
但对一段链式 Stream，如果里面混着缓存查询、数据库补查和 RPC，很少有人会在读代码时立刻意识到
这是一个典型的 N 次外部调用问题。等到数据量从几十条涨到几百条，延迟会直接被放大。

## 最常见的坑，不是“慢”，而是慢得没有边界

把远程调用混进 Stream，最危险的地方不只是性能下降，而是系统失去了清晰的控制点。

假设有一个订单列表接口，需要展示订单、用户昵称和最近一次物流状态。很多人会写成：

`orders.stream().map(order -> assemble(order, userClient.query(order.getUserId()), logisticsClient.latest(order.getId())))`

这段代码的坏处不是“不够优雅”，而是它把三个层次的问题揉在了一起：

1. 集合遍历是本地 CPU 行为。
2. 用户和物流查询是外部 I/O 行为。
3. 展示对象组装是纯内存转换行为。

当这三件事混在一个 `map` 里时，你几乎没法单独对远程调用做批量化、限流、熔断或降级。
它们跟着每个元素逐个触发，最后把接口耗时锁死在最慢的下游上。

更麻烦的是，这类代码很容易在压测前看不出问题。开发环境的数据量小、依赖服务快，
链式调用显得顺滑；到了生产环境，订单一页从 20 条变成 200 条，N+1 调用立刻放大十倍。
这时你再补救，往往不是改一行 lambda 能解决的，而是要整体拆开处理流程。

## 更稳的写法，是先把 I/O 收拢，再做内存转换

如果一段处理逻辑需要外部数据，通常更可靠的顺序是：

1. 先遍历本地数据，收集需要查询的主键集合。
2. 对外部依赖做批量调用，拿回结果并构造成 Map。
3. 最后再用 Stream 或普通循环做纯内存组装。

这样做的好处很直接。你可以明确知道外部调用发生了几次、每次打了多少数据、
失败后要不要降级、某个依赖慢了以后是否允许跳过某些字段。更重要的是，
内存转换这一层重新变回真正的“纯函数式”处理，Stream 的表达优势才成立。

比如订单列表场景，可以先收集 `userIds` 和 `orderIds`，分别调用批量用户接口和批量物流接口，
拿到两个结果 Map 以后，再写一段简单的 `stream().map(order -> toView(order, userMap, logisticsMap))`。
此时 `map` 做的只是对象拼装，而不是顺手发网络请求。代码依然清楚，但性能边界和失败边界都更明确。

## 并行 Stream 不是这类问题的解药

有人看到单条查询太慢，会进一步想到 `parallelStream()`。这通常只会把问题换个方式放大。

并行 Stream 适合 CPU 密集、无共享状态、可并发拆分的内存计算。远程调用并不符合这个前提。
一旦把 RPC 或数据库访问放到并行 Stream 里，线程数、连接池、下游限流阈值和超时传播就会纠缠在一起。
本来是“调用太多”的问题，最后变成“短时间内同时打太多”，把下游也一起拖慢。

更实际的风险是，你以为自己只是改了一个集合处理方式，实际上却改变了系统的并发模型。
原来串行时下游还能勉强扛住，改成并行后，接口高峰期可能突然出现连接池耗尽、线程堆积或熔断打开。
这种变化如果没有明确评估，很容易在业务高峰时变成事故。

## 判断标准很简单：lambda 里做的事，能不能只靠内存完成

我现在读这类代码时，会用一个很直接的判断标准：这个 lambda 里的逻辑，如果断网了还能不能正常跑完。
如果答案是否定的，那它大概率就不该被直接塞进 Stream 主链路。

这不是说 Stream 里绝对不能出现任何方法调用，而是要区分方法的性质。
像字段计算、状态映射、格式转换、金额汇总，这些都属于纯内存逻辑，放进 `map` 或 `filter` 没问题。
但只要方法背后可能走网络、查数据库、访问缓存或触发消息发送，就应该把它从流水线里拎出来，
变成显式的独立步骤。

这样做不是为了“反函数式”，而是为了让系统行为能被看见、被测量、被优化。

## 让代码短，不如让边界清楚

很多糟糕的 Stream 用法，本质上都来自一个误区：把“代码更短”误认为“设计更好”。
可在服务端开发里，真正重要的往往不是表达有多紧凑，而是副作用边界是否清楚，
外部调用是否可观测，异常语义是否一致，性能是否容易预估。

所以不要把远程调用混进 Stream 流水线。先把 I/O 操作独立出来，把批量查询、超时、降级和缓存策略放在显眼的位置，
再让 Stream 回到它擅长的部分：做集合上的本地转换。只有这样，代码的整洁才不是表面整洁，而是系统行为真正可控。

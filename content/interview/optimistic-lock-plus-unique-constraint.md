## 面试题一旦落到“扣库存”，答案就不能只背乐观锁

很多候选人被问到“怎么防止库存超卖”时，第一反应是乐观锁：
`UPDATE stock SET count = count - ? WHERE sku_id = ? AND count >= ?`，然后检查影响行数。
这个答案对了一半。面试官如果继续追问“乐观锁能不能兜住所有并发问题”，
不少人就会卡住，因为他们没有想过乐观锁只覆盖了一部分路径。

乐观锁解决的是“同一行数据被多个请求并发修改”的问题。
它的前提是这一行已经存在，而且能通过版本号或者条件判断来控制更新。
但真实业务里还有另一种常见情况：数据还不存在，多个请求同时想把这条记录“造”出来。
这时候没有版本号可比较，乐观锁天然使不上力，需要唯一约束来兜底。

## 扣库存场景里，哪些问题乐观锁管不了

扣库存不一定只发生在已经创建好的库存行上。拆开看，至少有三类场景：

第一类是首次初始化库存。活动刚开始，运营先按 SKU 建了一批库存，
如果初始化接口被并发调用，两条请求可能同时查不到记录、同时执行插入，最后产生重复行。
乐观锁没有参与条件更新，因为它根本没有旧值可以判断。

第二类是幂等写入。用户重复点击下单，同一个请求 ID 前后到达两次，
如果接口用“先查后插”的方式生成订单或扣减明细，两次查询都可能得到“不存在”的结果，
然后各自插入一条记录。这时业务上已经重复，但乐观锁看不到问题。

第三类是防止扣成负数。单纯用 `count >= ?` 作为乐观锁条件可以挡住大多数并发，
但如果同一 SKU 在多个表或缓存里各存一份余额，数据库只约束了主表的更新，
其他副本靠乐观锁就不够，最终一致性恢复时仍然需要唯一键或对账来发现重复。

这些问题的共同点不是“修改了同一行”，而是“同一业务语义可能被插入多次”。
乐观锁是行级更新工具，不是唯一性保证工具。

## 唯一约束为什么能兜底

唯一约束不是用来替代乐观锁，而是用来补上乐观锁管不到的最后一道闸门。
它把“这个业务只能有一份”变成数据库层面的硬规则，而不是应用层的君子协定。

比如扣减明细表可以在 `order_id + sku_id` 上加唯一索引，
重复订单就算绕过应用层判断，也一定会在插入时撞上唯一键，由数据库拒绝。
库存初始化可以在 `sku_id + biz_date` 上加唯一索引，两个并发首次插入只能成功一个，
另一个拿到冲突后走查询或重试，不会留下脏数据。

一个常用的做法是“唯一约束 + 冲突处理”：插入时捕获唯一键冲突，
如果已经存在就读取现有记录并继续做业务判断，而不是把冲突当成错误直接抛出。
这样既保持了接口幂等，又让应用在重复请求面前有明确的退路。

## 乐观锁和唯一约束如何配合

成熟的库存扣减流程，通常不是只靠某一个手段，而是按数据生命周期分层。

初始化阶段由唯一约束兜底，防止并发建行；
扣减阶段用乐观锁或者行锁控制同一行的并发更新；
落库之后再用请求 ID 的唯一索引防止重复消费；
最后定期跑对账，把缓存、明细、库存主表之间的偏差找出来。

每一层只解决自己的问题。乐观锁负责“同一行别改飞”，
唯一约束负责“同一笔业务别出现两份”。两者不是二选一，而是叠在一起。

## 面试时怎么答会更完整

如果面试官问“乐观锁扣库存为什么还需要唯一约束”，
可以先用一句话点题：乐观锁管的是更新路径，唯一约束管的是插入路径。

然后展开讲两个场景：并发首次插入库存、重复订单生成明细。
这两个场景都没有旧版本可以比较，乐观锁不能提供先到先得的保证，
只有唯一索引能在数据库层把第二个请求拦下来。

最后补一句生产经验：不要只在应用里写“先查再插”的判断，
除非数据库上有唯一索引，否则任何先查再插都存在竞态窗口。
这句话往往比背定义更能让面试官相信你处理过真实并发。

## 结论：乐观锁让更新安全，唯一约束让写入可信

库存扣减是经典并发题，但也是分层题。
乐观锁解决了高并发更新同一行的风险，却解决不了并发首次写入、重复请求和幂等问题。
唯一约束看似基础，实际是这些场景里最可靠的兜底。

所以真正稳的回答不是“我用乐观锁”，而是说清楚：
在更新路径上，我用乐观锁控制并发；在写入路径上，我用唯一索引保证幂等。
这样数据库才能既扛得住并发，又不会留下重复数据。

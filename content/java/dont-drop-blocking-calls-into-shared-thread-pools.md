## 线程池真正怕的不是“任务多”，而是“任务卡”

很多系统看起来是线程池不够用，实际上是任务里塞进了阻塞调用。
一旦某个任务在里面等数据库连接、等 HTTP 响应、等文件 I/O，线程就会一直被占着，
后面的任务只能排队。

问题不在于执行器本身，而在于你把“短计算”与“长等待”放到了同一条路上。

## 公共线程池适合短任务，不适合不可控等待

公共线程池通常承担的是一些轻量工作，比如消息回调、简单转换、聚合计算。
这些任务应该尽快开始、尽快结束，让线程持续流动起来。

如果把同步 RPC、磁盘写入、慢 SQL 这类任务也扔进去，线程池会被外部系统的波动带着走。
外部一慢，内部就一起慢，最后连本来很快的任务也被拖住。

## 更稳的做法是按等待类型隔离

可以按任务特征拆分执行器：

1. 纯计算任务用小而稳定的线程池。
2. 阻塞 I/O 任务单独隔离。
3. 依赖外部服务的任务单独设置超时和限流。

这样做不是为了“多建几个池子”，而是为了让慢任务的影响范围可控。

## 还要控制任务提交节奏

线程池隔离以后，仍然要看入口有没有失控。
如果上游持续把任务灌进来，就算每个任务最终都会完成，也可能把队列堆满。

所以通常还要配合：

- 有界队列。
- 明确拒绝策略。
- 超时和降级。
- 监控排队时长，而不只是活跃线程数。

## 一个简单判断标准

如果任务的等待时间明显大于计算时间，或者等待时间受外部系统影响很大，
就不要把它放进和核心业务共享的线程池里。

共享线程池应该保持“快进快出”，阻塞调用应该被隔离。

## 一个能卡住服务的正则

很多性能问题并不是出现在复杂系统里，而是出现在一行看起来很短的正则上。假设有一段用于校验用户名是否由字母、
数字和少量下划线组成的规则，有人会顺手写成下面这样：

```java
Pattern pattern = Pattern.compile("^(\\w+)+$");
```

对于普通输入，比如 `alice_2024`，这段代码几乎没有开销。可一旦传入一段很长的、末尾却不完全匹配的字符串，
匹配时间可能从几毫秒直接变成几十秒甚至更久。问题不在字符串本身有多复杂，而在正则引擎为证明“不匹配”这件事，
需要反复尝试大量不同的拆分方式。

这种现象叫灾难性回溯（Catastrophic Backtracking），是正则拒绝服务攻击（ReDoS）的常见根源。

## 回溯为什么会指数级爆炸

Java 的正则默认使用回溯式引擎。当模式里有多个可以重叠的量词时，引擎每遇到一个失败的位置，都会退回上一个
决策点，尝试另一种组合。`(\\w+)+` 就是典型结构：外层 `+` 和内层 `\\w+` 都能匹配同一串字符，于是同一个字符串
存在海量种拆分方式。

举一个更直观的例子。考虑模式 `^(a+)+$`，输入是一串 `a` 后面跟一个 `b`：

- 引擎先让内层 `a+` 吞下全部 `a`，再让外层尝试重复，发现剩下一个 `b` 无法匹配。
- 于是引擎退回一步，让内层只吞下倒数第二个 `a`，把最后一个 `a` 留给外层。
- 这个组合仍然失败，引擎继续退回，逐个改变每个 `a` 归属哪个量词。

随着 `a` 的数量增加，引擎需要尝试的组合数量会按指数级别增长。对几十个字符，可能已经是上亿次回溯。

关键在于：正则引擎并不知道“这种反复拆分没有意义”。它只会机械地穷举，直到穷尽所有可能或成功匹配。

## 先识别危险结构

修复之前，先把高风险写法认出来。下面几类模式最容易触发灾难性回溯：

- 嵌套量词：`(x+)+`、`(x*)*`、`(x+)*`。
- 可重叠的相邻量词：`\\d+\\d+`，两边都能匹配同一个数字。
- 带可选分支的重复：`(x|xy)+`，输入末尾不匹配时容易反复尝试。
- 很长且允许空匹配的重复：`(.*)*`。

识别时不要只看“有没有危险符号”，还要结合输入边界判断。一个只处理短字符串的规则，就算结构有风险，
实际危害也有限；真正危险的是把同样的正则用于用户可控、长度不受限的输入。

## 几种常用的修复方式

### 用原子组阻止回溯

原子组 `(?>...)` 会告诉引擎：一旦这部分匹配完成，就把它当成一个整体，不再退回内部重新拆分。

```java
Pattern pattern = Pattern.compile("^(?>\\w+)+$");
```

这样内层 `\\w+` 吞下最长匹配后，引擎不会再逐个字符退回尝试其他拆分方式，最坏情况从指数级降到线性级。

### 用占有量词

占有量词在普通量词后加一个 `+`，语义和原子组接近，表示“尽可能多地匹配，并且不回溯”。

```java
Pattern pattern = Pattern.compile("^\\w++$");
```

和原子组相比，占有量词写法更短，适合“先尽量吞掉、失败也不回头”的场景。

### 简化模式本身

很多时候危险来自模式写得比需求更宽。用户名校验其实不需要嵌套重复，直接写：

```java
Pattern pattern = Pattern.compile("^\\w+$");
```

只要允许的字符集合相同，这个版本不会产生重复拆分。先把需求说清楚，再决定是否需要那些“看起来更灵活”的写法，
通常是最省事的修复。

### 限制输入长度

如果业务上允许设置上限，优先在进入正则前就做长度校验：

```java
if (input.length() > 64) {
    throw new IllegalArgumentException("input too long");
}
```

长度限制不能消除回溯，但可以把最坏情况控制在可接受范围内。它更适合作为纵深防御的一层，而不是唯一手段。

## 不要依赖“提前拒绝”

有人会先判断字符串长度是否合理，再交给正则，觉得这样就安全了。但长度合理不代表结构安全。
一个一百字符的恶意输入，在灾难性回溯下仍可能耗尽线程时间。长度限制只能降低风险等级，不能替代对模式本身的修正。

同样，也不要只靠“先做一次快速预判”来拦截。很多 ReDoS 样本正是设计成前缀完全正常、只有末尾触发布尔爆炸，
预判逻辑很难稳定识别它们。

## 生产环境怎么兜底

即使把正则写规范了，仍建议给匹配过程加一个超时，避免任何单条正则长时间占用线程。可以借助独立线程加 `Future.get`，
或者使用支持超时的第三方正则库：

```java
ExecutorService executor = Executors.newSingleThreadExecutor();
Future<Boolean> future = executor.submit(() -> pattern.matcher(input).matches());
try {
    boolean matched = future.get(2, TimeUnit.SECONDS);
} catch (TimeoutException e) {
    future.cancel(true);
    // 记录告警并走降级分支
}
```

这种方式适合处理少量、低频、用户可控的匹配。对于高并发场景，为每条正则单独开线程的成本过高，更合理的做法是
在入口统一限制长度、使用经过审查的模式，并配合监控观察匹配耗时。

最后，把正则集中管理也很有价值。散落在各处的正则很难统一审计，集中到一个配置或工具类里，既方便代码审查，
也方便在发现危险模式后一次性修复。

## 正则的安全靠写法和边界一起保证

灾难性回溯不是正则引擎的缺陷，而是回溯式匹配在面对模糊模式时的固有特性。写出安全的正则，需要同时做几件事：
把嵌套量词拆开或换成原子组、根据真实需求简化模式、对输入长度设限，并为高风险匹配预留超时与降级。

最坏情况想清楚了，再谈最常用的性能优化，才不容易被一行正则拖垮整条请求链路。

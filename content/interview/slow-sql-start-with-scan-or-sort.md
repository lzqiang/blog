## 面试里一说慢 SQL，很多人马上跳到“建索引”

慢 SQL 确实常和索引有关，但如果面试时一听到“查询很慢怎么办”，第一反应只有“加索引”，通常说明排查思路还停留在背结论阶段。

更成熟的回答应该先把问题拆开：这条 SQL 到底是扫描的数据太多，还是排序代价太高？是过滤条件没压住数据量，还是回表把随机 I/O 放大了？是分页方式本身有问题，还是执行计划选错了索引？

只有先分清主要成本落在哪一类，后面的优化建议才不会泛。

## 先看扫描量，是因为很多慢根本慢在“读了太多没必要的数据”

数据库最常见的慢法之一，就是扫描行数远远大于最终返回行数。

例如一条查询最后只返回二十条记录，但执行过程中扫了几十万行。这个时候问题的重点不是“数据库性能不够”，而是过滤没起作用。可能是没有合适索引，也可能是索引顺序和查询条件不匹配，还可能是条件里做了函数计算、隐式类型转换，导致索引失效。

所以回答这类题时，我通常会先说：先看执行计划里的扫描行数和过滤比例，确认慢是不是因为读得太多。

如果核心问题就是扫描过大，那么优化方向往往是：

1. 调整索引顺序，让高选择性的条件尽早参与过滤。
2. 改写条件，避免在索引列上做函数或表达式计算。
3. 缩小查询范围，别把宽时间区间或低区分度条件全压给单条 SQL。

## 扫描不大也可能慢，因为排序和临时表一样能吃掉时间

有些 SQL 条件过滤得并不差，结果还是慢。这时候就要警惕另一个常见成本：排序。

如果 `order by` 不能利用索引顺序，数据库就可能需要额外排序，数据量一大，还会落到磁盘临时文件。面试时如果能主动提到 `filesort`、临时表和排序内存限制，区分度会明显高一些。

这类场景下，优化思路通常不是单纯补一个过滤索引，而是重新看“筛选条件 + 排序字段”能否共用一套索引顺序。否则就算过滤之后只剩几万行，排序成本也足以把响应时间拉长。

## 回表问题经常被忽略，但在线上很常见

还有一类 SQL，执行计划看起来“用了索引”，却依旧不快。原因常常是：虽然先走了二级索引过滤，但后面为了取非索引列，又回主键表拿完整数据，最终发生大量随机 I/O。

这就是很多人常说的“回表”。如果命中过滤条件的数据很多，回表次数一大，整体成本就会上去。

所以在面试里除了说“有没有索引”，还可以顺手补一句：要看是否出现大量回表，必要时考虑覆盖索引，或者把列表页查询拆成先查主键、再按需取详情的两段式方案。

这句话通常能说明你不只会背概念，而是知道 SQL 变慢时，成本可能藏在索引之后。

## 深分页常常不是数据库“突然变差”，而是查询方式本来就贵

如果题目提到翻页越来越慢，也别只停在“数据库数据量大了”。很多深分页问题，本质上是 `limit offset` 需要先跳过前面大量记录。哪怕最终只返回一页数据，数据库也得先处理前面那些被丢掉的行。

这时就该明确说：要区分普通慢 SQL 和分页模型导致的慢。后者很多时候要改分页方式，例如基于上次游标或主键范围翻页，而不是只指望数据库硬扛越来越大的 offset。

## 回答顺序比答案名词更重要

如果我要把这道题压缩成一个更像线上排查的回答，我会这样组织：

先看执行计划，判断主要成本是在扫描、排序、回表还是分页丢弃；再根据成本位置决定是改索引、改 SQL 写法，还是改业务分页模型；最后结合慢日志和实际返回行数，确认优化前后是否真的减少了数据库处理的数据量。

这样的回答会比“加索引、分库分表、上缓存”更扎实，因为它先讲了判断路径，再讲解决手段。

## 面试官真正想听的，通常不是你记得多少术语

慢 SQL 这类题目，表面是在问数据库知识，实际上更像在看你有没有排查思维。

能不能先拆成本位置，能不能区分现象和根因，能不能知道哪些优化只是延后问题、哪些优化是在真正减少数据库工作量，这些才是回答里最有价值的部分。

所以被问到慢 SQL 时，别急着背万能答案。先分清它到底慢在扫描多，还是慢在排序重。只要这个起手式对了，后面的分析通常就不会偏。

## 异步一多，最难排查的常常不是异常

做 Java 服务时，很多人一开始担心的是线程池大小、超时配置和重试次数。等系统真的跑起来以后，反而更难缠的问题常常来自另一头：多个异步步骤在偷偷共享同一份可变对象。

这种问题麻烦就麻烦在，它未必每次都出错。压测时可能偶尔正常，开发环境里也不容易复现，但线上一旦并发上来，就会冒出字段被后一步覆盖、日志里看到的值和最终落库值对不上、任务顺序看似正确却得到错误结果之类的问题。

## 共享可变状态为什么危险

所谓共享可变状态，最常见的样子是：主流程里创建了一个 DTO、Map 或聚合对象，然后把它传给多个异步任务，让这些任务边查数据边往里面填字段。

表面上看，这样可以省去很多参数传递，也避免每一步都创建新对象。但代价是，你把多个任务之间的边界打碎了。谁先执行、谁后执行、谁覆盖了谁，不再只由代码顺序决定，而是由线程调度、远程调用时延和 CPU 抢占共同决定。

只要对象还是可变的，这种不确定性就会直接变成结果不确定。

## 线上最常见的三个坏味道

第一种是“同一个对象被多次补写”。例如先查用户信息，再异步查订单摘要和优惠资格，两个任务都拿着同一个 `UserView` 去写字段。代码看着集中，结果却可能因为某一步晚到，把已经写好的值又改掉。

第二种是“集合边遍历边追加”。有人会把一个 `ArrayList` 或 `HashMap` 交给多个异步分支共同写入，以为最后 `join` 一下就可以统一收结果。问题在于这些容器本身并不保证并发写安全，就算没抛异常，也可能出现丢元素、覆盖值或顺序混乱。

第三种是“把上下文对象跨线程传太远”。比如在请求线程里构建一个上下文，然后一路透传到 `CompletableFuture`、批处理回调和消息消费逻辑里，谁都能改一点。最终出问题时，你已经很难判断到底是哪一步把状态污染了。

## 更稳的做法是让每一步只产出结果，不改共享对象

我更推荐把异步流水线写成“每一步返回自己的结果，最后再汇总”的样子。

例如：

1. 一个任务只负责查用户基础信息，返回 `UserProfile`。
2. 一个任务只负责查订单摘要，返回 `OrderSummary`。
3. 一个任务只负责查营销资格，返回 `PromotionEligibility`。
4. 主流程在所有任务完成后，统一组装最终响应对象。

这样做的好处是，每个异步任务只有输入和输出，没有对外部状态的隐式修改。你既容易测试，也容易在日志里定位是哪一步结果不对，更不容易因为线程切换把对象写乱。

## 如果必须共享，至少把边界收紧

现实里也不是所有场景都能完全避免共享对象。比如某些高性能批处理里，你可能确实想复用缓冲区或复合上下文。这时候至少要做三件事。

第一，明确谁拥有写权限。不要让多个异步分支都能自由改同一份状态。

第二，把共享范围压到最小。只在一个局部阶段共享，不要让对象跨越太多线程和生命周期。

第三，优先使用不可变对象或拷贝后的快照。与其赌大家都“只改自己那一小块”，不如直接把可写性关掉。

## 比起补锁，更重要的是先改写法

很多团队遇到这类问题后的第一反应是加 `synchronized`、换并发容器，或者在对象写入处补一层锁。这些手段有时能止血，但往往只是把症状压住，没有消掉根因。

因为真正的问题不是“写的时候没加锁”，而是异步任务之间本来就不该依赖一份随时会变的共享状态。写法如果还是错的，锁只会让吞吐下降，代码也更难懂。

## 异步设计先问一句：这一步是否必须改外部状态

我现在看异步代码，最先问的不是线程池配得够不够大，而是：这一步到底是在生产结果，还是在偷偷修改别人持有的对象。

如果答案是后者，通常就值得停下来重构一下。先把共享可变状态消掉，再谈并发优化，很多偶发性 bug 会直接少掉一大半。这类改动不一定显眼，但对系统稳定性往往比多调几个线程参数更值。
